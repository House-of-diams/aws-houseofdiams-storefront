## Approved data source

The user designated staging AWS RDS as the final authoritative source for storefront catalog, variant prices, and inventory data. The older Supabase restore differences are intentional; they are not a reason to copy or reconcile Supabase values into RDS. Checkout must price from RDS values. This decision supersedes the earlier F7 price/stock-source question.

The owner subsequently confirmed that **everything currently sold on the storefront, including promotional gifts, is made to order**. Physical `stock_quantity` must not decide whether any current storefront item can be placed or paid. Preserve the existing inventory tables and history; do not delete them merely to implement this rule. If the business later introduces genuinely limited-stock items, that is a new explicit product/checkout policy, not an inference from current stock counts or `product_lane`.

## Historical read-only audit findings (before applied F7 SQL)

- The RDS connection was verified as `hod_app` inside `BEGIN READ ONLY`. `public.customer_identities`, `customer_sessions`, and `customer_profiles` exist. `public.categories` and `order_status_history` do not; `catalog_categories` exists.
- `orders`, `checkout_attempts`, `coupon_redemptions`, `carts`, and `wishlists` still have `user_id` foreign keys to `auth.users`. `profiles.id` also references `auth.users`. There is no `customer_identity_id` on the inspected commerce tables. The F6 Keycloak identity ID cannot be passed into the existing `user_id` columns. Guest token ownership is present in orders and checkout attempts.
- Checkout/payment direct tables have broad `hod_app` grants but no applicable direct RLS policies in the inspected set. Existing atomic functions are `SECURITY DEFINER`, owned by `hod_migration`, and executable by `hod_app`. Grants alone do not make direct queries work.
- `create_pending_order_v2` takes `p_user_id uuid` and validates exactly one of legacy user ID or guest hash. The signed-in F6 customer contract therefore needs a reviewed new ownership column/function path. The current guest path must remain independent.
- **Blocking inventory mismatch:** `order_items` has both `order_items_reserve_inventory` and `trg_apply_order_stock_on_create` after-insert triggers. `reserve_pending_order_item()` records a reservation; `apply_order_stock_on_create()` also decrements `products.stock_quantity` immediately. Later `finalize_paid_order_with_coupon_secure()` calls `finalize_paid_order_with_inventory_secure()`, which checks and decrements the same stock again. Thus the current path can charge stock twice for one paid order. `restore_order_stock_on_cancel()` restores stock only when order status changes to `cancelled`; the checkout dismissal function updates `gateway_order_status`, not status. This behavior needs a reviewed, tested SQL repair before any RDS checkout/payment switch.
- The existing RDS `claim_payment_webhook_event`, `claim_payment_recovery_action`, and `release_order_inventory_reservation` definitions were read. Signature presence alone is not a payment regression test. Payment subunit, coupon, finalization, refund, and exactly-once behavior still require focused verification.
- Current checkout pricing rejects a paid line when requested quantity exceeds `products.stock_quantity`. A free-gift coupon is independently rejected when gift stock is below one or the paid and gift quantity together exceed stock. Home/shop promotion banners also hide the gift at stock below one. RDS currently has one active free-gift coupon, `HOUSEOFDIAMS2026`, for `princess-halo-stud-earrings` (standard lane, active, stock 94); the owner confirmed that gift is made to order. Active RDS products currently occupy only the `standard` lane; one active product has zero stock. This does not prove that all future products are jewelry or unlimited.
- The reconciliation cron calls `expire_inventory_reservations`, which marks reservations expired and marks pending gateway orders expired. It does not restore the legacy stock decrement. Cancellation releases reservations and marks the gateway order dismissed, but likewise does not restore stock. Payment failure releases reservations. Admin/manual order inserts also encounter the table-level order-item stock trigger; a repair must scope behavior explicitly rather than silently changing admin order semantics.
- **Blocking payment-subunit mismatch:** storefront `toRazorpayAmountInSubunits()` uses factor 1 for JPY and factor 100 for the other supported currencies. The live RDS `finalize_paid_order_with_inventory_secure()` computes `round(payment_amount * 100)` without a JPY branch, so a valid JPY capture can fail finalization with `payment_amount_mismatch`. This must be repaired and tested alongside the inventory change, while retaining order ID, amount, currency, and captured-state validation.
- **Security finding, permission-only remediation verified:** initial read-only checks found default `PUBLIC` execution on the F7 `SECURITY DEFINER` functions. The user applied the scoped 15-function ACL migration and the `hod_app` verification now shows no `anon`/`authenticated` execution on that set. This finding concerned database privileges, not proof that anonymous HTTP clients had database credentials. New or replaced functions in later F7 SQL must still preserve these ACLs or explicitly revoke default execution in the same transaction.
- **Success-page RLS gap:** `hod_app` has `SELECT` grants on `checkout_result_page` and `checkout_result_states`, but their only current RLS policies target `anon` and `authenticated`; read-only `hod_app` queries see zero rows. The ownership forward draft now adds narrowly scoped `hod_app` SELECT policies for enabled content. The intended rows still need post-SQL verification. Existing `catalog_categories` and `contact_info` are readable.

## Permission-only migration applied and verified

`aws-f7-function-acl-forward.sql`, `aws-f7-function-acl-rollback.sql`, and `aws-f7-function-acl-verify.sql` contain the narrow 15-function package. On 2026-10-10 the user ran the forward file in staging pgAdmin as the migration role and reported `COMMIT`. A fresh `hod_app` read-only RDS check independently verified all 15 functions: nine current storefront-direct functions are executable by `hod_app`; six internal functions are not; none of the 15 is executable by `anon` or `authenticated`; function ownership and `SECURITY DEFINER` remain as audited. This ACL change did not alter table data, grants/RLS, inventory behavior, or payment logic. Do **not** rerun the forward file. The rollback exists for an explicitly reviewed recovery only. Admin-only functions remain outside this F7 ACL package. This is permission hardening, not the full F7 checkout migration.

## JPY correction applied to staging

The storefront already rejects non-USD charges without a live Fixer rate; the JPY issue is independent of rate availability. The user applied `aws-f7-jpy-subunits-forward.sql` to staging and reported COMMIT. Fresh read-only checks through verified TLS confirmed that the installed finalizer uses whole yen for JPY and hundredths for other currencies, retains the made-to-order branch, `SECURITY DEFINER`, owner `hod_migration`, `search_path=public`, and restricted execution. This does not validate an actual payment or enable F7 checkout.

## Remaining F7 SQL and code work

The ACL, customer-ownership, made-to-order, JPY, and order-history forward files are already applied to staging; do not rerun them. `scripts/test-f7-sql-preflight.mjs` expects absent F7 columns and is now obsolete for the migrated staging schema; do not rerun it. SQL COMMITs are not behavioral payment validation, and `CREATE OR REPLACE FUNCTION` must retain the restricted grants.

The made-to-order migration is now applied to staging: `orders.fulfillment_mode` has a `legacy_stock` default. New F7 storefront orders would explicitly use `made_to_order`; old/admin/manual orders keep their existing behavior. Read-only checks confirmed the column, constraint, zero orders, six patched functions, and restricted execution on the four security-definer payment functions. The two ordinary trigger functions retained their pre-existing broader EXECUTE grants. The stock behavior still needs isolated regression testing. The separate JPY patch is also applied and metadata-verified, but payment behavior remains untested.

The ownership proposal adds `customer_identity_id` foreign keys to orders, checkout attempts, and coupon redemptions, while retaining legacy `auth.users` columns/FKs and guest hashes. It extends the existing atomic pending-order and coupon-finalization functions; a new customer-owned order has exactly one owner, and a customer/idempotency unique index separates signed-in attempts. The proposal narrows direct `hod_app` grants and adds role-only RLS policies for the checkout tables the current application uses directly. These true predicates trust the server role across customers, as F6 does; every ported route must derive the customer ID from the verified HttpOnly F6 session and apply its own owner predicate. Browser roles receive no new policies. Rollback refuses to discard customer-owned orders, attempts, or redemptions. `profiles.id`, carts, wishlists, and admin identity are unchanged; cart/wishlist persistence needs separate review before they can use customer identity.

The order-history proposal adds the missing audit table, trigger, `hod_app` read policy, and existing-order backfill. Rollback refuses to delete any history rows. The success-page category query should use the existing `catalog_categories` table after row/order parity is checked; no second categories table is proposed.

**Read-only local code slice:** `HOD_F7_RDS_READ_PREVIEW=true` only takes effect while `HOD_CUSTOMER_AUTH_ENABLED=true`, so the existing F6 proxy still blocks order placement. Under this temporary preview, checkout tax, quote, and coupon read from RDS through parameterized SQL; the shared pricing calculation skips physical stock limits for made-to-order paid items and gifts. Checkout profile resolves only the server-verified F6 session and reads `customer_profiles`; it does not accept a browser-supplied customer ID. RDS CMS gift banners ignore stock only in preview. Both flags remain OFF in the saved environment. Preview is not the final checkout/payment transport or a release gate.

**Historical implementation state before the latest code pass:** placement/idempotency, cancellation, payment verification, success/order history, webhook processing, failure handling, and captured-payment recovery used Supabase. The prepared RDS branches are now implemented; disabled legacy branches remain intentionally until F9. Quote/coupon/tax need full representative regression beyond the sampled HTTP checks. F6 Keycloak UAT is outstanding. No customer-owned RDS order was created and no real payment or webhook was sent. F8 reconciliation is outside this phase and was not changed. Do not apply the SQL proposals as a substitute for write-path review and testing.
