# AWS storefront cache and request audit

Reviewed 2026-10-12. Source inspection only; no production traffic measurement, deployment, SQL changes or application changes performed for this audit.

## Findings

| Area | Current implementation | Consequence |
| --- | --- | --- |
| Navbar, bulk homepage data, compact product cards, default search suggestions | `unstable_cache` with 300-second revalidation | Repeated reads can reuse Next's Data Cache when the deployment supports it. |
| Many public CMS API routes | `force-static` and `revalidate = 300` | Production route responses can be reused. Development timings do not establish production cache behavior. |
| Submitted nonempty product search | Uncached result loader; API returns `private, no-store` | Repeating the same search repeats database work. Cached search reference data does not cache the results. |
| Product detail and related products | React `cache()` request memoization; detail page is `force-dynamic` | Duplicate work within a render can be avoided, but there is no five-minute cross-request product-detail cache. |
| Filtered/paginated product cards | `getStorefrontProductCardPage` lacks a persistent result cache | Repeated filter/page combinations can repeat database hydration. |
| Fresh homepage hero, shop-by-category and Instagram data | Fresh reads supplement cached homepage data | The homepage is not entirely covered by its bulk cache. |
| Announcement bar, footer content, FAQ, service banner, settings and promotion popup/offer APIs | Dynamic routes calling RDS repositories | These do not have the same five-minute route cache as the static CMS endpoints. |
| Maintenance/routing state | Coalescing process cache with a 30-second lifetime | Cache is local to each process. |
| Redis | Used for rate limiting | No shared Redis product/CMS response cache was found. |

### Avoidable duplicate requests

`components/home/SelectedCouponOffer.tsx` loads on mount, window focus and visible document state. The focus and visibility events can both fire when returning to a tab. There is no shared in-flight promise or freshness window, and the fetch uses `no-store`. React development Strict Mode can also cause an extra mount effect. These mechanisms explain possible duplicate calls, not an unlimited polling loop.

Separate settings consumers and repeated contact-content consumers also lack a common browser read cache. A cached server endpoint can still receive multiple HTTP requests without making multiple database reads.

### Database amplification

`lib/repositories/product-repository.ts` runs 23 parallel SELECTs for product hydration, in addition to the initial product SELECT and optional dropdown-option reads. This is bulk hydration, not a separate query for each product. Nonempty search calls `getCanonicalSearchImageUrls`, which hydrates full product data to select images. Consequently a single search request can generate dozens of SQL queries.

### Admin updates

No storefront `revalidateTag`/`revalidatePath` invalidation integration was found. Time-based expiry refreshes on demand; it is not a background timer. Layered browser/CDN caches and stale-while-revalidate can extend when a visitor observes a change. An admin integration outside this repository was not inspected.

## Recommended implementation order

1. Add shared browser freshness and in-flight deduplication for public CMS reads; consolidate coupon focus/visibility refreshes.
2. Cache public search, product-detail and filtered-card results for 300 seconds, with bounded keys and entries. Preserve existing price, variant, image and filtering normalization. Avoid caching oversized full-catalog objects.
3. Cache reusable catalog lookup data and reduce search image hydration while preserving canonical image selection.
4. Apply a consistent public CMS policy, keeping maintenance responsive and checkout, payment, coupon validation and private account reads authoritative.
5. Integrate authenticated admin invalidation, retaining TTL as fallback. Verify cache persistence and sharing for the actual AWS runtime and CloudFront policies.
6. Validate identical results before/after, concurrent-request deduplication, warm-cache SQL reduction, expiry/admin updates, and a production-mode navigation trace.

## Interpreting the reported 50,000 daily requests

The user identified a Supabase or database dashboard, but the exact metric, period and originating application remain unknown. HTTP requests, SQL statements, database connections and media requests are different measurements. Current migrated storefront reads use RDS; a Supabase total may instead reflect the old live site, admin, historical traffic or another client. The existing `SUPABASE_REQUEST_VOLUME_AUDIT.md` describes an earlier migration state and must not be treated as current runtime evidence.

If confirmed to be database reads generated by one ordinary visitor, 50,000/day warrants investigation. Source inspection found amplification and duplicate opportunities, but no evidence establishes a continuous public CMS polling loop or attributes that total to this storefront.

Ask DevOps for the exact metric and a time-bounded breakdown by application, endpoint and SQL operation, together with origin request counts and cache hit/miss information. Do not include credentials, session tokens or request bodies in diagnostic logs.
